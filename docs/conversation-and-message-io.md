# Conversation and message IO

Messages cross one boundary: `send_message({to, message, kind?, reply_to?, deadline_ms?})` and `gateway.ingest(sender, envelope)`. [Gateway Design](gateway-design.md) describes the implementation ownership; [Kernel Contract](kernel-contract.md) is normative. [Implementation Status](implementation-status.md) separates shipped behavior from proposals.

The former Conversation, Lease and engagement lifecycles were removed without replacement. Their design history remains in git, not as an alternate message path.

## Identity (#1569)

Every mounted channel is one `(platform, identity)` instance, `identity` being `bot` or `owner`. The bot identity is the default for reading and answering on every platform. The Owner's own account is a second instance of the same platform: it reads what the Owner can see, so a mention of the Owner or a message to the Owner reaches the Resident even where no bot is present, and it sends only on the Owner's explicit instruction. That instruction is an authenticated fact (the sending turn originates from an Owner-tier prompt and the instance's declared grant allows outbound), never prose: text cannot select the Owner's account. Every send journals the identity it went out under.

Contact identity is identity-independent: actor endpoints are keyed by platform and external id, and the same person is the same actor whether the bot or the Owner instance saw them. A message both instances see is one event. A message this process posted through the Owner instance is not an inbound Owner prompt.

Shipped by #1569 PR 5: the instance axis (`ChannelInstance.identity`, surfaces mounted as `<platform>:<identity>`, routes keyed by instance), the `as: bot | owner` selector on `send_message` with the `identity_not_granted` refusal, and the Slack Owner instance for sending. Lane 6 (`feat/1569-owner-intake`) adds the account's own listener on Slack (RTM) and Discord (user gateway) under a per-instance intake posture (`settings.intake`: `mentions_and_dms` default, `all`, `none`): a DM to the Owner or a mention of the Owner reaches the Resident as `receivedBy: owner`; where an Owner instance reads a platform (the grant's `ownerIntake`) a mention of the registered Owner is addressed under a mention-only grant whichever instance observed it; the account's own messages are never an outside event; reactions are not intake; one physical message seen by both instances is routed once. Lane 7 (`feat/1569-owner-only-platforms`) adds Instagram and KakaoTalk as Owner-only platforms (no bot account; reached through the `owner` arm alone) and the reply door's Owner path: a surface reachable only through `<platform>:owner` is answered as the Owner when the declaration's `autoReply` says so, otherwise the answer is refused `message.resident.reply_draft` and stays the Resident's draft for the Owner to send — the default (since #1600 lane R2 the Resident delivers that draft to the Owner); a bot instance always answers as the bot. The Owner-origin fact is read off the sending turn's own deliveries and the actor registry; the outbound grant is the instance's declaration. Lane 5b (`feat/1569-login-helpers`) adds `oni login <platform>`: the Owner's own sign-in through the SDK's flows (Slack QR, Discord remote-auth, Instagram password and second step, KakaoTalk passcode), declared over the Owner's socket as a `channel_add` frame and sealed into the vault by the daemon. Lane 9a (`feat/1569-webhook-contact`) adds the `webhook:<id>` contact kind on `send_message`: a declared webhook target's URL receives the letter as a signed JSON body under one-attempt custody (never a redirect followed; a url takes Owner consent), its textual answer is returned on the tool result, and `unknown` joins the contact outcomes for a letter that may have landed. Lane 9b (`feat/1569-linear-provider`) adds Linear as a hand-rolled, Owner-only provider (a personal API key is the Owner's, so the instance is `linear:owner` under the identity axis): signed, fresh, deduplicated webhook ingress of new issues and comments at `/linear/webhook` under the declared posture (`mentions_and_dms` reads the comments that name the Owner, `all` everything; the ingress `event: linear`, `mention` when the Owner is named), replies as the Owner's comments on the issue under the reply door's Owner path with an id derived from the idempotency key and looked up before posting, the Owner's own actions never an outside event, the router's refusal answered 200. Lane 9c (`feat/1569-a2a`) adds A2A on the 0.3 JSON-RPC binding: one inbound door for every declared peer (`POST /a2a`, the card at the well-known path) where a peer's `message/send` becomes one inbound message with its context as the conversation (an agent admitted at its contact's tier, not a bot echo) and the reply door's answer completes the context's newest open task, and the `a2a:<id>` contact kind on `send_message` whose answer — the peer's message or its task read back until it settles, with `thread` for `reply_to` to continue the exchange — rides the tool result. Shipped coverage per platform is recorded in Implementation Status.

This withdraws the W2 #1110 identity amendment (only the Owner is public, the agent has no persona, replies go out as the Owner, draft by default). Where a platform forbids automation under a user account, the Owner instance stays read-only and egress degrades to the draft-then-Owner-taps-send path of the Kernel Contract.

## Platform transport

Platform I/O is the agent-messenger SDK: one SDK listener and client per instance, logged in with credentials the vault opened (`login({...})`; the SDK's own credential store is never used). The SDK owns sockets, reconnects, acks and the Web API; the pinned build is the repository's fork, taken at one commit for byte uploads, per-client retry control and authenticated attachment downloads. Discord bot, Discord Owner and Telegram bot SDK clients use `retries: 0`; Slack pins its inner Web API client to one attempt while its SDK retains three attempts for explicit 429 refusals. The channels package keeps facts-only normalization, inbound dedupe, delivery custody, rendering and chunking, and the typed `sent | not_sent | unknown` evidence folded from SDK errors. GitHub and signed-webhook ingress are not messengers and stay hand-rolled. Inbound attachments arrive as platform references; with `ONI_MACHINES_INBOX` (or `machines.inbox`) configured, the composition root best-effort stores bot-authenticated Telegram `file_id` and Slack file-ID downloads (`files:read`) and public URLs such as Discord CDN links through its separate media resolver before handoff, then rewrites successful references to `<machine>:<path>`. Authenticated downloads have a 50 MiB cap and deadline; storage keys distinguish conversations and exclusive-create writes refuse an existing leaf or symlink. A failed fetch or write keeps the platform reference and warns; Slack Owner and private-URL-only references remain unfetched. Implementation Status records shipped coverage.

## Inbound facts and contact identity

A driver authenticates platform origin and submits facts: event id, physical channel/workspace, external addressees, DM status, reply/thread/ancestor metadata, structured payload, rendered text, and the identity that received it. Only the gateway resolves `(surface, externalId, workspace)` to an actor, derives standing and classifies the addressee as bot, Owner or ambient. Self-reported roles are not authority.

Owner-declared channel grants remain a ceiling. A personal tier takes precedence over a channel default, never over a blocked channel. Broadcast input remains evidence-only. Default observer standing does not authorize instructions. Blacklist refusal precedes Wait correlation and ordinary surface routing.

Opted-in provisional contact minting is bounded by the existing channel policy and rolling window. It records observed identity, not promoted authority, and stays evidence-only. Durable Person declarations and credentials are owned by [Provisioning and Providers](provisioning-and-providers.md).

## Two doors out

A turn that came from a conversation answers in that conversation through the reply door: the result text goes back to the channel and thread the person wrote in (a DM in its chat, unthreaded), as the bot, with no model tool call. If only the Owner instance can reach that conversation — or the prompt was a DM the Owner's account received, an inbound-only Owner instance included — the reply is sent as the Owner where the declaration auto-replies, and otherwise delivered to the Owner as a draft through a messenger bot or the socket on a platform the Owner has; a letter to the Owner never needs a budget or consent (#1600 lane R2). On GitHub the conversation is the issue or pull request (`owner/repo#N`) and the answer is a comment there; a button tap is answered on the message the button was on.

`send_message` is for every other party: an existing session, a new child session, a CLI agent, or a contact on another channel, person or conversation than the one the work came from. Its `contact` target carries the surface, the conversation and, by explicit instruction, the identity. A letter addressed to the very conversation that prompted the turn is refused before the gateway (`same_conversation`): that conversation is answered by the plain reply. A driver never turns a returned handler value into a platform response: the final assistant answer enters the gateway as an origin-targeted send whose authority is the router's conversation binding, not a grant (shipped by #1569 PR 4; see Implementation Status).

## Delivery

Session mail becomes a prompt at atomic inbox commit and passes the receiving session's prompt pre-policy. New child configuration and first mail share that commit. Session delivery has no external receipt classification.

A letter to a platform reached only through the Owner's account is refused `identity_not_granted` before transport unless sent `as: owner` from an Owner-origin turn (#1600 lane R3); a delivery the platform rejected, or whose outcome is unknown, is the contact outcome on the tool result. Actor sends use existing grants (a Person's `reach`, the Owner's standing grant from `contact_add`; #1569 lane 8), exact endpoint resolution, egress budget (a reachable target with no active budget takes the Owner's consent on the `send_message` invocation, bound to the Person row; `message.resident.approval_required` denies it otherwise) and stable platform idempotency keys. Their executed values distinguish accepted, rejected and unknown. The reply door shares the delivery custody (one admission fact per message id, one physical attempt per key) but neither a grant nor a budget: a reply is never outreach.

WebSocket admission receipts and later message frames are distinct. Rendering and chunking remain provider-owned, after admission.

## Correlation and terminal mail

Explicit reply/message ids, thread ids, token hashes and external conversation ids retain their deterministic Wait precedence. Same-tier ambiguity is refused; structured requested actions remain data for the Wait fold. Physical surface routing is independent of conversation correlation.

A child terminal crosses gateway admission, then atomically appends one parent inbox message preserving final text, terminal kind and original reply binding. Processes transport session ids and committed doorbells; they have no parallel settlement or acknowledgement lifecycle. The parent interprets the returned letter; no task-satisfaction authority is recreated.

Deadlines are durable alarm rows. Answer and timeout compete on one source-action CAS; late replies remain input. Startup expiry is wired. Continuous live alarm dispatch is #947, not a second timer in message IO.

## Approval and remaining proposals

The existing executor consumes typed authenticated approval answers bound to the captured request, input hash and generation. Gateway authentication transports evidence; it does not execute a protected body or invent a policy verdict. Free prose is not approval evidence.

#969 unified the request lifecycle and #949 removed the approval tool: Owner consent is a `require_approval` policy row on `provision.contact_promote`/`contact_merge`. That work did not implement unified lifecycle replacement, broader contact promotion automation, a new negotiation budget, or a new conversation store. Additional rendering/disclosure UX and first-contact autonomy require their own approved policy changes.
